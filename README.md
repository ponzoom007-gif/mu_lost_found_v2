# MU Lost & Found

ระบบแจ้งของหายและพบสิ่งของ ใช้ Python 3.9+, Flask, JavaScript และ SQLite/PostgreSQL

## เริ่มพัฒนาในเครื่อง

ติดตั้งใน virtual environment หลังได้รับอนุญาตจากเจ้าของโปรเจกต์:

```sh
python -m pip install -r requirements.txt
```

กำหนด `APP_ENV=development` และเอา `DATABASE_URL` ออกจาก environment และ `.env` หากต้องการใช้ SQLite เท่านั้น จากนั้น:

```sh
python -m flask --app app init-db
python app.py
```

เปิด `http://127.0.0.1:5001` เปลี่ยนที่เก็บ SQLite ได้ด้วย `SQLITE_PATH` การ import แอปและการเริ่มเซิร์ฟเวอร์จะไม่สร้างตารางหรือรีเซ็ตรหัสผ่าน ต้องรัน `init-db` อย่างชัดเจน

## การเปลี่ยนแปลงและผลต่อผู้ใช้

- แอดมินใช้รหัสผ่าน hash ปกติ ไม่มีรหัสตายตัวหรือการให้สิทธิ์ตามชื่ออีเมล ตรวจสิทธิ์ปัจจุบันจากฐานข้อมูล
- ทุกฟอร์ม POST ตรวจ CSRF token; ออกจากระบบด้วย POST
- Google Login ตรวจ `state` อายุ 10 นาที ใช้ได้ครั้งเดียว และตรวจ `email_verified`
- บัญชีเดิมและบัญชีสมัครด้วยรหัสผ่านต้องยืนยันอีเมลผ่าน Google หนึ่งครั้ง แล้วตั้งรหัสใหม่ที่ `/account/password` รหัสก่อนยืนยันจะถูกยกเลิกเพื่อป้องกันคนอื่นสมัครด้วยอีเมลเจ้าของจริงไว้ก่อน บัญชีแอดมินที่ตั้งผ่าน CLI ถือว่าผู้ดูแลยืนยันแล้ว
- เปลี่ยนรหัสผ่านได้ภายใน 10 นาทีหลังล็อกอิน Google ใช้ขั้นต่ำ 12 ตัวอักษร ถ้าใช้เฉพาะ Google สามารถข้ามได้ ไม่มีการส่งอีเมลจากระบบ
- จำกัดคำขอเข้าสู่ระบบด้วยรหัสผ่าน 10 ครั้งต่อ 15 นาที ทั้งต่อ IP และอีเมล เก็บตัวนับในฐานข้อมูลร่วมกันทุก worker
- Production ใช้ PostgreSQL ที่กำหนดเท่านั้น หากเชื่อมต่อไม่ได้ตอบ 503 ไม่มีการเปลี่ยนไปฐานชั่วคราว
- รูปใหม่รองรับ PNG/JPEG/WEBP สูงสุด 5 MB ต่อไฟล์, 20 ล้านพิกเซล และ 16 MB รวมทั้งคำขอ เปิดอ่านรูปจริงแล้วแปลงเป็น JPEG พร้อมลบ metadata; ยังไม่รองรับการอัปโหลด HEIC/HEIF
- Cloud Storage ขัดข้องจะปฏิเสธการบันทึก ไม่เปลี่ยนไปเก็บในเครื่อง รูปใหม่ที่บันทึกข้อมูลไม่สำเร็จจะถูกเก็บกวาด รูปเก่าจะถูกลบหลัง commit สำเร็จ
- โพสต์ซ้ำใช้รหัสคำขอที่ฐานข้อมูลบังคับ unique พร้อมตรวจ fingerprint ข้อมูล คำขอใหม่ใช้ชื่อเดิมได้
- ค้นหาและกรองในฐานข้อมูลก่อนแบ่งหน้าละ 9 รายการ กดปุ่มค้นหาหรือ Enter; ลิงก์หน้าถัดไปคงตัวกรองเดิม
- `/health` คืนเพียงสถานะพร้อมใช้งาน; `/db-status` จำกัดเฉพาะแอดมิน

## เตรียม production (ต้องดำเนินการโดยผู้มีสิทธิ์)

ยังไม่มีการรันขั้นตอนเหล่านี้กับฐานข้อมูลจริงในการแก้โค้ดนี้:

1. สำรองฐานข้อมูลและไฟล์ ตั้งช่วงบำรุงรักษาก่อนเปลี่ยนเวอร์ชัน
2. ตั้ง `APP_ENV=production`, `DATABASE_URL` เป็น DSN ที่ถูกต้องจากผู้ให้บริการ, `SECRET_KEY` ใหม่ที่สุ่มอย่างปลอดภัย, `SUPABASE_URL`, `SUPABASE_KEY` และ `SUPABASE_BUCKET` ไม่ใส่ความลับลง Git
3. ตั้ง `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` และ `GOOGLE_REDIRECT_URI` ให้ตรงกับ URL callback ที่อนุญาตใน Google Console
4. ติดตั้ง requirements และรัน `python -m flask --app app init-db` กับฐานที่เลือก คำสั่งเพิ่มตารางประกอบ/index และคอลัมน์รุ่นเก่าโดยไม่รีเซ็ตรหัสผ่าน สำรองไว้ก่อนเสมอ
5. ตั้งรหัสแอดมินใหม่ด้วย `python -m flask --app app set-admin EMAIL` แทน EMAIL ด้วยอีเมลจริง รหัสผ่านถูกถามแบบซ่อนและไม่ส่งเป็น argument
6. Deploy ผ่าน Gunicorn แล้วตรวจ `/health`, Google Login, การอัปโหลด และการสร้างประกาศใน staging ก่อนเปิดบริการ

การเปลี่ยน `SECRET_KEY` ทำให้ session เดิมใช้ไม่ได้ ทุกคนต้องล็อกอินใหม่ รหัสแอดมินและ key ที่เคยอยู่ในซอร์สต้องเปลี่ยนในระบบจริงด้วย การแก้ไฟล์อย่างเดียวไม่หมุน credentials ที่ deploy อยู่

ฐานข้อมูลกับ Storage ไม่ใช่ transaction เดียวกัน หากการลบไฟล์บน Cloud ล้มเหลวหรือ worker ถูกหยุดกลางทาง อาจมีไฟล์ค้าง ต้องตรวจเก็บกวาดไฟล์ที่ไม่มีประกาศอ้างอิงเป็นงานดูแลระบบ ยังไม่มีคิว retry ถาวรสำหรับการลบไฟล์

## การทดสอบ

```sh
python -m unittest discover -s tests -v
node --check static/js/script.js
```

ชุดทดสอบใช้ SQLite ใน temporary directory และจำลอง Google/Storage ไม่โหลดค่าจริงจาก `.env` และไม่ติดต่อฐาน production

CI ใน `.github/workflows/tests.yml` เตรียมรันชุดเดียวกันกับ SQLite และ PostgreSQL service แยกสำหรับทดสอบ เมื่อต้องการทดสอบ PostgreSQL ในเครื่อง ตั้ง `TEST_POSTGRES_URL` ไปยังฐาน `mu_lost_found_test` บน localhost เท่านั้น ชุดทดสอบสร้าง schema สุ่มของตัวเองและลบเฉพาะ schema นั้นหลังจบ

การทดสอบ SQLite ผ่านในเครื่องไม่ได้ยืนยันว่า PostgreSQL/Google/Supabase ที่ deploy อยู่พร้อมใช้งาน ต้องตรวจ staging เพิ่มก่อนปล่อยจริง
